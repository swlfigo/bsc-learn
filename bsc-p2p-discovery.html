BSC 节点是怎么找到彼此的

一个新节点第一次启动时谁也不认识，从这里走到连上第一个节点，一共 17 步。前 11 步都是 UDP 小包：先向引导节点问路，再一轮轮向外扩散；后 6 步才是 TCP 连接和握手。可以点“下一步”逐步看，也可以直接点图上的箭头。

基于 bnb-chain/bsc v1.8.2，commit 54afaff4d，行号以该 commit 为准。整体架构见 BSC 节点源码线路图。

一个候选节点要过的关卡

换个角度看同一个过程：任何一个节点，从被 A 知道到成为 A 的连接，都要依次通过下面这些检查。右边是在这一关被淘汰的情况。

  1. 进入路由表UDP

    来源：引导节点、本地数据库里的旧节点、问路得到的节点。

    p2p/discover/table.go:561 handleAddNode
    进不去的情况
    • 对应的桶满了（每桶 16 个）：先进候补名单（最多 10 个），等有节点失联再补上
    • 同一 /24 网段超限：每桶最多 2 个，全表最多 10 个
    • 自己的路由表还没初始化完时，不收主动找上门的节点
  2. 被随机游走选中本地

    路由表初始化完成后，eth 层不停地在里面随机漫游，产出候选节点。

    eth/backend.go:1012 setupDiscovery
    这一步不淘汰节点。
  3. 索要名片（ENR）UDP

    问路得到的只有地址和公钥，要向对方本人要名片，才知道它是哪条链的节点。

    p2p/discover/v4_udp.go:358 RequestENR
    被淘汰
    • 对方不响应，或者没有完成地址验证
  4. ForkID 检查本地

    名片里的 eth 字段带着 ForkID，由创世哈希和已经过的硬分叉算出。

    eth/protocols/eth/discovery.go:71 NewNodeFilter
    被淘汰
    • 名片里没有 eth 字段
    • ForkID 不兼容：以太坊或其他链的节点，没跟上硬分叉的旧版本 BSC 节点
  5. 拨号检查本地

    拨号器有空余出站名额时才取候选。默认最多主动拨 16 个（MaxPeers 50 ÷ 3）。

    静态节点从这一关直接进入，并且优先拨
    p2p/dial.go:418 checkDial，p2p/server.go:590
    跳过
    • 出站名额已满：先等着
    • 是自己；名片里没有 TCP 端口
    • 正在拨、已经连着、对方正在连进来
    • 不在 --netrestrict 范围内；35 秒内拨过
  6. TCP 拨号TCP

    连对方名片里的 IP 和 TCP 端口。

    p2p/server.go:48 拨号超时
    失败
    • 15 秒内连不上：端口没开、被防火墙挡住、NAT 没做端口映射
  7. RLPx 加密握手TCP

    交换临时密钥，之后所有数据加密；确认对方公钥就是它的节点 ID。

    p2p/server.go:957 setupConn，p2p/transport.go:40
    断开
    • 5 秒内没完成
    • 对方公钥和预期的节点 ID 不符
  8. 连接数检查本地

    TrustedNodes 里的节点不受这一关的上限限制。

    p2p/server.go:800 postHandshakeChecks
    断开
    • 总数已到 MaxPeers（默认 50）
    • 对方是连进来的，而入站名额（34 个）已满
    • 重复连接；连到了自己
  9. Hello：交换支持的协议TCP

    BSC 节点支持 eth/68、eth/70、snap/1、bsc/1、bsc/2。

    p2p/server.go:815 addPeerChecks
    断开
    • 没有共同协议
    • 客户端名称匹配了 --peerfilter
  10. eth Status：确认是同一条链TCP

    比对网络 ID（主网 56）、协议版本、创世哈希、ForkID，校验 TD。

    eth/protocols/eth/handshake.go:110，:166
    断开
    • 任何一项不符
  11. 扩展握手与准入TCP

    等 snap、bsc 扩展协议就绪，再做最后的数量检查。TrustedNodes 和 EVN 节点免检。

    eth/handler.go:441 runEthPeer
    断开
    • snap 同步时，不支持 snap 的节点比支持的多出 5 个以上
    • 总数超过 MaxPeers，或同一 IP 超过 MaxPeersPerIP
  12. 成为 peer

    开始收发区块、交易和投票。节点数据库记下它，下次启动直接当种子。

    eth/dropper.go，p2p/server.go:59，:62
    之后可能断开的情况
    • 连接数满时，每 3 到 7 分钟随机断开一个已连 10 分钟以上的普通节点，腾出位置
    • 30 秒收不到任何消息，或 20 秒发不出一条消息

路由表怎么从 6 个长到上百个

第 6 到 8 步每一轮都在做同一件事：从已经认识的节点里，挑离目标最近、还没问过的 3 个去问。每个节点回答的都是它所知道的离目标最近的节点，所以一轮比一轮近，直到问不出更近的为止。这里的“距离”是节点 ID 的异或距离，跟地理位置无关。

之前已认识 这一轮新认识 这一轮去问的节点

示意图，点的数量不是真实数据。实际上每次查找只保留离目标最近的 16 个结果，查找过程中收到的节点都会加进路由表（p2p/discover/lookup.go:121，table.go:737）。

几个容易混淆的地方

引导节点要开 TCP 吗？

不需要。第 1 到 11 步全是 UDP，A 用 TCP 连的是 C 这样的普通节点。引导节点名片里的 TCP 端口如果是 0，拨号器会直接跳过它，不会出现连接失败（p2p/dial.go:421）。

引导节点是专门的程序吗？

不是。可以用仓库里的 cmd/bootnode（209 行，只做 UDP 发现），也可以直接用普通 geth：每个没加 --nodiscover 的节点都会回应 PING 和 FINDNODE。官方引导节点唯一特殊的地方，是地址被写进了 params/bootnodes.go 当默认值。

第二次启动还需要引导节点吗？

基本不需要。节点数据库 <datadir>/geth/nodes 记着最近见过的节点，重启时取最近 5 天内的最多 30 个当种子（table.go:60）。删掉这个目录，就回到第一次启动的状态。

别人怎么发现我？

就是第 4、5 步反过来：你向别人问路时，对方验证了你的地址并把你记进路由表，以后再把你介绍给别人。但想被别人连上，你的 TCP 端口必须能从公网访问。

UDP 30303TCP 30303结果
通通能发现别人、能被发现、能被连接，最多 50 个连接
通入站被挡能发现别人也能被发现，但别人连不进来：最多 16 个连接（全是你主动拨的），别人还会白白来拨你
完全不通任意问不了路，找不到别人，也没人知道你；只能靠静态节点手动连接

自己动手看

下面的命令能看到图里每一步真实发生的样子。devp2p 是本仓库自带的调试工具。

# 第 2 到 11 步：打印节点发现的每一个包
geth ... --vmodule "p2p/discover=5"
# 日志里会出现 >> PING/v4、<< PONG/v4、>> FINDNODE/v4、<< NEIGHBORS/v4

# 本节点的地址和名片
geth attach ./node/geth.ipc --exec 'admin.nodeInfo.enode'
geth attach ./node/geth.ipc --exec 'admin.nodeInfo.enr'

# 第 10、11 步：向某个节点要名片
go run ./cmd/devp2p discv4 requestenr "enode://...@IP:端口"
# 第 12 到 14 步：测 TCP 连接和握手，成功会打印对方的客户端名和版本
go run ./cmd/devp2p rlpx ping "enode://...@IP:端口"

# 当前连接数，以及其中有多少是别人连进来的
geth attach ./node/geth.ipc --exec 'admin.peers.length'
geth attach ./node/geth.ipc --exec 'admin.peers.filter(p => p.network.inbound).length'
