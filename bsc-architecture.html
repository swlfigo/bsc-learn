分层与代码量

BSC 是 go-ethereum 的分叉，目录结构基本沿用上游。BSC 自己的改动集中在共识（Parlia）、投票（core/vote）、出块（miner 中的 MEV 部分）、系统合约和 bsc 网络子协议。下面的条长按非测试 Go 代码行数绘制（单位：千行），所有层用同一比例尺；深色条、带 BSC 标记的是 BSC 新增或大幅改写的包。

Parlia 出块

Parlia 是权益权威证明（PoSA）：一小组验证者按固定顺序轮流出块，验证者集合由链上质押合约选出，每个 epoch 更新一次。共识引擎在 consensus/parlia，接口实现见 Prepare / FinalizeAndAssemble / Seal / VerifyHeader。

轮到谁出块

验证者按地址排序。区块 N 的正当值（in-turn）验证者是 validators[(N+1) / TurnLength % len]，每人连续出 TurnLength 个块。正当值块难度为 2，其他验证者补出的块难度为 1。snapshot.go:466，parlia.go:93

验证者 A 连续 16 块（450ms × 16 = 7.2 秒）
验证者 B 连续 16 块
验证者 C …

TurnLength 从 Bohr 开始由 ValidatorContract 的 getTurnLength() 决定，写在 epoch 块的 Extra 里。代码注释列出的典型值：默认 1 或 4，Lorentz 为 8，Maxwell 为 16。

正当值验证者缺席时：backoff

出块时间戳 = 父块毫秒时间 + BlockInterval + backOffTime。正当值验证者的 backoff 为 0；其余验证者（排除最近签过块的、Bohr 起也排除正当值本人）用 N / TurnLength 作种子随机排序，第 k 个等待 初始延迟 + k × 1000ms。Lorentz 后初始延迟为 2000ms。parlia.go:2351，ramanujanfork.go:31

正当值+0ms
备选 1+2000ms
备选 2+3000ms
备选 3+4000ms

“最近签过”的定义：在最近 (N/2+1) × TurnLength − 1 个块里已经出过 TurnLength 个块的验证者不能再出块（SignRecently，snapshot.go:243）。这保证任意时刻至少要有过半验证者参与才能延续链。

验证者集合轮换

每 epoch 的第一个块（epoch 块）在 Extra 里写入下一组验证者及其 BLS 公钥，来源是 ValidatorContract.getMiningValidators()。新集合不是在 epoch 块立即生效，而是延迟到 number % epochLength == minerHistoryCheckLen() 时才切换，给网络留出确认时间。snapshot.go:374，parlia.go:1960

Snapshot 是 Parlia 的核心状态：当前验证者、最近签名者 Recents、TurnLength、BlockInterval、EpochLength，以及最近一次投票证明 Attestation。内存 LRU 缓存 1280 个，每 1024 块以 JSON 存入数据库（key 为 parlia- + 哈希）。snapshot.go:40–148

系统交易

每个块的末尾都有几笔由验证者自己发出的系统交易：发往系统合约、gas 价格为 0、发送者等于 coinbase。出块时 FinalizeAndAssemble 生成并签名它们；导入时 StateProcessor 先把它们挑出来不执行，交给 Parlia.Finalize 重算一遍并逐笔比对哈希。普通交易出现在系统交易之后会被判为非法（Cancun 起）。parlia.go:323，:1433；core/state_processor.go:136

Finalize 的执行顺序：

  1. 按硬分叉升级系统合约字节码（TryUpdateBuildInSystemContract，Feynman 后在 Finalize 内执行）
    core/systemcontracts/upgrade.go:1147

    parlia.go:2075，feynmanfork.go:33
  3. 如果本块不是正当值出的，且正当值验证者最近没签过：调用 SlashContract.slash 记录缺席
    parlia.go:1471
  4. 分配手续费：所有手续费先进入 SystemAddress，再通过 ValidatorContract.deposit 给出块验证者（Kepler 之前另有 1/16 给 SystemReward 合约）
    parlia.go:2022

快速最终性

BEP-126 在 PoSA 之上加了一层 BLS 投票：验证者对每个新块投票，票数达到 ⌈2N/3⌉ 后由下一个出块者聚合进区块头。连续两个块都拿到足够票数时，前一个块就被最终确认（finalized），不会再被回滚。

  1. 新区块头验证通过后，VoteManager 收到 HighestVerifiedHeaderEvent。同步中或刚开始挖矿的 40 个块内不投票
    core/vote/vote_manager.go:97
  2. 检查三条规则：同一高度只投一票；256 块内不出现包围投票（新票的 source–target 区间包住旧票，或反过来）；只投规范链头
    vote_manager.go:255
  3. 用 BLS 密钥签名 VoteData{source, target}，先写投票日志再进投票池，并通过 bsc 协议的 Votes 消息广播
    vote_signer.go:32，vote_journal.go，eth/handler.go:969
  4. 下一个出块者在 Seal 时从 VotePool 取票，凑够 ⌈2N/3⌉ 后聚合签名，连同投票者位图写进 Extra
    parlia.go:1073
  5. 其他节点导入时验证聚合签名，并在 Snapshot 里更新：target 成为 justified；如果 source + 1 == target，source 成为 finalized
    parlia.go:472，snapshot.go:199

RPC 可查询：parlia_getJustifiedNumber、parlia_getFinalizedNumber。如果投票池里已经有子块的足够票数，GetFinalizedHeader 会提前给出更新的 finalized 块。parlia.go:2286，api.go:78

违规投票的监控（--monitor.maliciousvote）和双签监控（--monitor.doublesign）目前只记日志，节点代码不会自动提交证据；链上通过预编译 0x68 验证双签证据。core/monitor/

导入与分叉选择

所有节点（不论是否是验证者）都走导入线。入口是 BlockChain.InsertChain，大部分检查都并行进行：签名者恢复、区块头校验、区块体的几项检查、状态预取都在各自的 goroutine 中。core/blockchain.go:2217–2826

  1. 并行恢复交易发送者；BSC 上先做 blob 数据可用性检查（sidecar 数量、版本哈希、KZG 证明）
  2. engine.VerifyHeaders 并发校验 Parlia 规则，ValidateBody 校验交易根和 blob gas
  3. ProcessBlock：预取器先在临时状态上跑一遍交易加热缓存；StateProcessor.Process 执行普通交易，系统交易交给 Parlia.Finalize，最后检查 Payment Lane
  4. ValidateState 并行校验 bloom、收据根和状态根
  5. writeBlockAndSetHead：先做分叉选择，再写入区块、收据、sidecar 和状态，必要时 reorg

分叉选择规则

BSC 用 justified 高度优先的分叉选择（ReorgNeededWithFastFinality，core/forkchoice.go:129）。比较两条链的链头时：

  1. justified 块高度更高的链胜出（Plato 之后）。
  2. 相同时比较总难度 TD。因为正当值块难度为 2、补出块为 1，TD 高意味着正当值块更多。
  3. TD 也相同时：高度更低者胜；高度相同则时间戳更早者胜；仍相同且是同一出块者（双签），哈希更小者胜，否则随机。

校验模式 --tries-verify-mode：local 完整校验状态根；none 等模式不维护 trie（NoTries），跳过部分检查以换取性能。core/verify_mode.go

MEV

BSC 的 MEV 是“验证者 + 外部 builder”模式：builder 在节点外组装交易，提交给当期验证者；验证者把它和本地打包的块比较，选收益最高的签名出块。代码中有两种提交方式，并存运行。本仓库没有 bundle 池，也没有 eth_sendBundle。

Bid（BEP-322）Bid Block（BEP-675）
提交内容一组交易 + 报价完整区块：头、交易、sidecar，末尾附未签名的系统交易
接口mev_sendBidmev_sendBidBlock 或 gRPC SendBidBlock（端口 8552）
验证者是否执行是：simBid 完整模拟，可用本地交易补满（GreedyMergeTx）签名前不执行，只做头部、TxHash、系统交易形状和存款金额的轻量检查
择优标准实际奖励最高GasFee 最高，且区块奖励和验证者奖励都要胜过最佳 bid，手续费高于本地块
出错处理模拟失败即丢弃先广播、后用 InsertChain 校验；失败则吊销 builder 24 小时，多数验证者举报也会吊销
生效条件Mev.Enabled另需 Mev.BidBlockEnabled 且已过 Pasteur（2026-08-25）

时间线

一切都在一个出块间隔（450ms）内完成。bid 必须在 bidBetterBefore = 父块时间 + 间隔 − DelayLeftOver − BidSimulationLeftOver 前到达（默认留 15ms + 20ms）。更好的 bid 会打断正在进行的模拟，但剩余时间少于 NoInterruptLeftOver（约 135ms）时不再打断。common/bidutil/bidutil.go:11，miner/bid_simulator.go:436

Payment Lane

BEP-703，随 Jenner 硬分叉启用（Chapel 测试网 2026-10-29 已激活，主网 2026-12-08）。每个块为“支付类”交易（主要是普通转账）保留一段 gas 配额。这段配额只能给支付交易用，用不完就空着，普通交易不能占用。所以即使合约交易拥堵，转账也总有空间。core/paymentlane/paymentlane.go

系统交易预留
普通交易与支付交易都可使用
支付配额
0配额 = ratio × GasLimit / 10000，ratio 介于 1 到 1000（即最多 10%）GasLimit

每个节点在导入时检查：GasUsed + max(0, 配额 − 支付交易已用 gas) ≤ GasLimit。配额不写入区块，各节点从父状态里的 PaymentLane 合约（0x…2007）读取 ratio 和名单后各自计算。

交易如何分类

按以下顺序判断，命中即停止（core/paymentlane/classify.go:35）：

  1. 系统交易、创建合约的交易、blob 交易和 7702 交易：普通。
  2. to 在 PaymentLane 合约登记的名单里：支付。
  3. 转账金额为 0：普通。
  4. to 是合约（有代码）：普通。
  5. 其余情况（向外部账户转账）：支付。

worker 打包顺序不变；只是普通交易如果会挤占剩余配额就跳过，同一发送者后续交易也一并跳过。miner/worker.go:965

网络与同步

P2P 层沿用 go-ethereum（discv4/discv5 发现、RLPx 加密传输、DNS 节点列表），默认端口 30303、最多 50 个连接。上面跑三个子协议：

协议版本作用
eth68、70区块和交易的广播与请求。BSC 的 eth/70 握手仍保留 TD，用于 Parlia 链同步；NewBlock 和 BlockBody 中可选携带 blob sidecar
snap1快照同步：按范围拉取账户、存储、字节码和 trie 节点
bsc1、2BSC 专有：Votes 投票广播；bsc/2 新增 GetBlocksByRange，一次最多取 64 块

节点第一次启动时怎么找到别的节点、怎么建立连接，见单独的分步流程图：BSC 节点是怎么找到彼此的。

广播策略

  • 区块：完整块发给 √N 个节点（DirectBroadcast 时发给全部），另外必发所有代理节点和 EVN 节点；其他节点只收哈希公告。eth/handler.go:774
  • 交易：只发给非 EVN 节点。小于 4096 字节的非 blob 交易整包发送，其余只发哈希。eth/handler.go:911
  • 投票：逐张发送给代理节点、EVN 节点和 TD 相近的节点；接收端每节点限速 68 票/秒。eth/handler.go:969

EVN（验证者增强网络）

验证者和它的哨兵节点之间组成一张高速网。Maxwell 后验证者把自己的节点 ID 登记在 StakeHub 合约里；本节点每 10 秒对照链上名单和白名单，把匹配的连接标记为 EVN。EVN 和代理节点被视为受信任节点，不受连接数和单 IP 限制。eth/handler.go:390，:888；p2p/peer.go:647

同步

chainSyncer 至少要有 5 个节点（10 秒后降为 1 个），选 TD 最高的节点同步。领先不超过 2 TD 时只等待 2 秒再检查（BSC 特有，避免出块间隔太短时频繁触发同步）。落后较多时 downloader 做 full 或 snap 同步，headers、bodies、receipts 并发下载；追上后由 fetcher 逐块导入。eth/sync.go:148–249，eth/downloader/downloader.go:651

阅读路线

第一次读代码，建议按下面的顺序：先搞清对象从哪来，再沿导入线走一遍（所有节点都会执行），最后看验证者独有的出块、投票和 MEV。

  1. eth/backend.go 的 New()：所有核心对象的创建顺序与依赖关系
  2. consensus/parlia/snapshot.go：理解验证者集合、轮次和最终性状态，后面所有逻辑都依赖它
  3. core/blockchain.go 的 insertChain 和 ProcessBlock：导入主干
  4. core/state_processor.go 和 parlia.go 的 Finalize：系统交易如何被分离与重放
  5. core/forkchoice.go：分叉选择
  6. miner/worker.go 的 commitWork，配合 parlia.go 的 Prepare、Delay、Seal：出块
  7. core/vote/ 全部 4 个文件，加上 parlia.go 的 assembleVoteAttestation 和 verifyVoteAttestation：最终性
  8. miner/bid_simulator.go、miner/bid_block.go：MEV
  9. eth/handler.go、eth/handler_bsc.go、eth/protocols/bsc/：网络传播
